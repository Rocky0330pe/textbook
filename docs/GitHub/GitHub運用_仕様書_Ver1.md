# GitHub 運用 仕様書 Ver1

教科書（『物理を理解するための数学』全9巻・ガイドブック2冊・物理シリーズ）の LaTeX ソースを GitHub で管理し、PDF を GitHub Actions で組むときの決まりです。移し方の手順は「GitHub移行_手順書_Ver1.md」にあります。教科書の中身の決まり（判型・章の型・表記・仕上げのきまり）は、これまでどおり `docs/仕様書/教科書制作_仕様書.md` と追補に従います。

## 1. 目的と方針

1. **ソースを1か所にまとめる。** 版ごとの zip を渡し合う形をやめ、GitHub の1つのリポジトリを「正本」にする。どの版も、タグから同じ PDF を組み直せるようにする。
2. **組版環境を固定する。** これまでの制作環境（Ubuntu 24.04・TeX Live 2023・固定版の LuaTeX-ja）を、GitHub Actions でそのまま再現する。
3. **正式な PDF は「何もないところから組んだもの」とする。** 前に組んだときの記録（`.aux`・ルビの位置の記録 `.ltjruby` など）が残っていると、組み上がりが変わることがある（9章）。Actions は毎回まっさらな状態から組むので、その結果を正とする。
4. **委員会の進め方は変えない。** 指摘の洗い出し → 委員の話し合いで修正方針 → 直す → 委員会の確認 → 議事録、の流れはそのまま。GitHub では「直す」を作業用のブランチで、「確認と取りこみ」をプルリクエストで行い、議事録は `docs/議事録/` に入れる。
5. **納品物の形は変えない。** PDF・tex 一式（zip）・検算ファイル（問題の追加・訂正があったときだけ）・議事録（md）。名前のつけ方も第9巻のときと同じ（7・8章）。

## 3. 組版環境（固定）

| 項目 | 版 | 入れ方 |
| --- | --- | --- |
| OS | Ubuntu 24.04 LTS（GitHub の `ubuntu-24.04` ランナー） | |
| TeX | TeX Live 2023（Ubuntu の apt。`texlive-binaries 2023.20230311`、パッケージ群 `2023.20240207`） | `apt-get install --no-install-recommends` で `texlive-base` `texlive-binaries` `texlive-latex-base` `texlive-latex-recommended` `texlive-latex-extra` `texlive-fonts-recommended` `texlive-pictures` `texlive-science` `texlive-lang-greek` `texlive-xetex` `latexmk` |
| フォント（欧文・数式） | TeX Gyre Schola・Heros（`fonts-texgyre`）、Latin Modern Math（`fonts-lmodern`） | apt |
| 和文フォント | BIZ UD明朝・ゴシック、Klee One | リポジトリの `tex/fonts/`。組むときに `~/.fonts` にも写す（`luatexja.cfg` の既定の和文書体を探すため） |
| LuaTeX-ja など | LuaTeX-ja 20231230.0、luaotfload v3.24、lualibs v2.76、lua-uni-algos v0.4、lualatex-math v1.12 | リポジトリの `texmf/`。`TEXMFHOME` をここに向ける |
| ツール | `pdfinfo`（`poppler-utils`）、`fc-cache`（`fontconfig`）、Python 3（標準ライブラリだけ） | apt（Python はランナーに入っている） |

**推奨パッケージは入れない（`--no-install-recommends`）。** `fonts-texgyre` は `fonts-texgyre-math` を推奨しており、これが入ると数式の書体が TeX Gyre Schola Math に切りかわって（`bk-b5.sty` が「あれば使う」書き方のため）全巻の組み上がりが変わる。ワークフローは、入っていたら組まずに止まる。`texlive-fonts-extra` も入れない。

**版を上げるとき**：TeX Live・LuaTeX-ja・Ubuntu の版を上げるのは「全巻にかかる修正」として委員会で決める。上げたら全巻を組み、ページの変化を議事録に残してから `main` に入れる。

**Mac では正式な PDF は作らない。** MacTeX は LuaTeX-ja などの版がちがい、`ci-build.sh` が使う道具（`timeout`・`pdfinfo` など）もそろっていない。組んで確かめるのは、委員会の作業環境（Linux）か Actions で行う。

## 4. 組み方（`scripts/ci-build.sh`）

```
scripts/ci-build.sh 対象…    対象：1〜9（数学の巻）・guide（ガイドブック2冊）・p1〜p5（物理）・all（1〜9 と guide）
```

1冊ごとの流れは、委員会がこれまで手で行ってきた手順と同じです。

1. `python3 gen.py`（もくじ・親ファイルを作る）
2. こわれたルビの記録（途中で切れた `.ltjruby`）があれば消す
3. `lualatex` を2回（ルビの位置とページ参照のため。まっさらな状態から2回で落ち着くことを確かめた：9章）
4. `tools/check_pages.py N`：もくじに書いたページと、実際のページを照らす
5. ずれがあれば `tools/syncpages.py N` → `gen.py` → `lualatex` 2回 → もう一度照らす（最大2回。PDF がない・エラーがあるときは行わない）。合わせたときは警告を出し、その巻の値を `out/pages_actual_N.json` に保存する。**その値を `pages_actual.json` に写してコミットする**（巻ごとに別のファイルにしてあるので、全巻を組んだときも、ほかの巻の値を消さずに写せる）
6. カバー展開図（`wrapN.tex`）を組む
7. ログを集計する（下の表）。結果は `out/`（PDF・ログ・`summary.md`・`check_pages_N.txt`）

| 確認すること（仕上げのきまり 1 のうち機械でできるもの） | 合格 | Actions で赤（失敗）にするか |
| --- | --- | --- |
| PDF ができたか | できた | する |
| 組版のエラー（ログの `!`）と、ルビの記録の読みこみの失敗 | 0 | する |
| もくじのページのずれ | 0 | する |
| はみ出し（Overfull \hbox が 1.7 pt をこえるもの） | 0 | しない（表で見る） |
| 未定義の参照・ない章（`BKPAGE missing`） | 0 | しない（表で見る） |

ルビのつけ忘れ（`tools/check_ruby.py`）、常用漢字外、見開きでの目視、委員ごとの観点の確認は、これまでどおり委員会が行う（Actions は代わりにならない）。

**メモリ**：1冊を組む lualatex は最大で約 5.3 GB（第2巻・第3巻。6章の計測）。ランナーのメモリは 8 GB なので足りるが、余裕は大きくない。第9巻は章ごとに Lua のごみ集めをする仕組み（`vol9-body.tex` の `\bkinputchap`）で約 2.8 GB に抑えている。ほかの巻にも入れる（全巻にかかる修正事項 No.58）。

## 5. GitHub Actions（`.github/workflows/build.yml`）

### 5.1 いつ組むか

| きっかけ | 組むもの | 結果 |
| --- | --- | --- |
| プルリクエスト | 変わった巻だけ（5.2） | Artifacts（7日間）。プルリクエストの画面に合否が出る |
| `main` への push（プルリクエストの取りこみを含む） | 変わった巻だけ（5.2） | Artifacts（7日間） |
| リポジトリに初めて入れたときの push | 組まない（初回は手動で組む） | ― |
| 手動（Actions →「組版」→ Run workflow） | 入力した巻（既定は `guide`。`all`・`6 7` など） | Artifacts（7日間） |
| タグ `volN-verM` の push | 第N巻 | リリース（8章） |
| タグ `guide-verM` の push | ガイドブック2冊 | リリース |
| タグ `pN-verM` の push | 物理第N巻 | リリース |
| タグ `all-YYYY-MM-DD`（例 `all-2026-11-01`） | 全巻とガイドブック | リリース（版の欄は日付） |
| それ以外のタグ（例 `migration-2026-10-31`） | 組まない | ― |

- `docs/`・`checks/`・README だけを変えたときは組まない（無料枠の節約）。
- 同じプルリクエストに続けて push したときは、古い実行を止める。手動の実行・`main` への push・タグの実行は止めない（途中の巻が組まれないままになるのを防ぐ）。
- タグは、組んだジョブが**すべて成功したときだけ**リリースを作る。
- プルリクエストを取りこむと `main` への push として変わった巻が組まれ、そのあとタグをつけると同じ巻がもう一度組まれる（同じ巻を2回組む）。6章の見積もりはこれを含めている。

### 5.2 どの巻を組むか（`scripts/changed-targets.py`）

| 変わったファイル | 組む巻 |
| --- | --- |
| `tex/chN-*`・`tex/volN*`・`tex/wrapN.tex` | 第N巻 |
| `tex/guide-*`・`tools/mkguidetables.py` | ガイドブック |
| `tools/mkmap9.py`・`tools/mkseriesidx.py` | 第9巻 |
| `pages_actual.json` | 値が変わった巻だけ |
| `tex/p1-*`・`tex/phN*`・`tex/phwrapN.tex` | 物理第N巻 |
| `phys/`・`tex/bk-phys*` | 物理第1巻（本文があるのは第1巻だけ） |
| 組み上がりに効く共通の部品：`tex/bk-*`（物理用を除く）・`tex/series-data.tex`・`tex/fonts/`・`tex/img/`・`texmf/`・`series.py`・`gen.py`・`tools/syncpages.py`・`tools/check_pages.py`・`scripts/ci-build.sh` | 第1〜9巻とガイドブック |
| ワークフロー（`build.yml`）と、組み上がりに効かないスクリプト（`changed-targets.py`・`name-pdfs.py`） | ガイドブック（いちばん短い試し） |

プルリクエストでは、作業用のブランチが `main` から分かれた所からの差分で判定する（あとで `main` に入ったほかの直しで、関係のない巻を組まないように）。比較元のコミットが見つからないとき（ブランチを強制的に書きかえた場合など）は、警告を出してガイドブックだけを組む。

### 5.3 ジョブ

| ジョブ | 中身 |
| --- | --- |
| 組む巻を決める（plan） | 5.1・5.2 の表で、組む巻の一覧を作る。手動の入力は、決まった名前（1〜9・guide・p1〜p5・all）だけを受けつけ、重なりを除く |
| 組む（build） | 巻ごとに1つのジョブ（同時に最大5つ）。TeX Live をインストール（推奨パッケージなし。`fonts-texgyre-math` があれば止まる）→ luaotfload のキャッシュを読む → `ci-build.sh` → 結果の表をジョブの Summary に出す → PDF などを Artifacts（`pdf-N`）に保存。失敗・時間切れのときはログも保存（`log-N`）。1ジョブの上限は 240 分 |
| リリース（release） | タグのときだけ。8章の形でリリースを作る |

使うアクション：`actions/checkout@v5`・`actions/cache@v5`・`actions/upload-artifact@v6`・`actions/download-artifact@v7`（どれも Node.js 24 で動く版。GitHub は 2026年9月23日にランナーから Node.js 20 を外した）。

## 6. 時間と無料枠

| 項目 | 値（2026年10月31日に GitHub の文書で確認） |
| --- | --- |
| 非公開リポジトリのランナー | Linux 2コア・メモリ 8 GB・SSD 14 GB |
| 無料プランの Actions | 毎月 12 ドル分（Linux 2コアは 1 分 0.006 ドルなので、約 2,000 分） |
| Artifacts の保存 | 500 MB（全巻とガイドブックの PDF は1回で約 65 MB。7日で消える設定） |
| 1ジョブの上限 | 6 時間 |
| 同時に動くジョブ | 20 まで（この設定では 5 に制限） |
| 使い切ったとき | 支払い方法を登録していなければ、翌月まで Actions が止まる（GitHub から 90%・100% でメールが来る） |
| 公開リポジトリ | 標準のランナーは無料（時間に数えない） |

組むのにかかった時間（委員会の作業環境で、まっさらな状態から計測。GitHub のランナーも同じ2コアだが、速さが同じとは限らない。これにインストールなどの準備が1ジョブあたり数分足される）：

| 対象 | ページ | 時間（lualatex 2回とカバー） | 最大メモリ |
| --- | --- | --- | --- |
| ガイドブック2冊 | 35＋103 | 約 5 分（72秒＋217秒） | 約 3.8 GB |
| 第1巻 | 403 | 約 6.5 分（391秒） | 約 4.7 GB |
| 第2巻 | 459 | 約 8.5 分（498秒） | 約 5.3 GB |
| 第3巻 | 567 | 約 13 分（769秒） | 約 5.3 GB |
| 第9巻 | 643 | 約 16 分（968秒） | 約 2.8 GB |

**見積もり**：1冊を組むと、準備を入れて約 10〜20 分。全巻とガイドブックを1回組むと約 2〜3 時間分（10ジョブの合計）で、同時に5つ動くので待ち時間は約 40〜60 分。

**1か月の目安**：無料枠（約 2,000 分）で、全巻をまとめて組むのは月に数回まで。ふだんは「変わった巻だけ」を組むので、1冊の Ver2 の作業（プルリクエストで数回＋取りこみ＋タグ）は1冊あたり 100 分前後に収まる見込み。足りなくなりそうなときは、(1) 全巻の手動の実行を減らす、(2) 依頼者の判断でリポジトリを公開にする、(3) 支払い方法と上限額を設定する、のどれかにする。

## 7. 版の番号・ブランチ・タグ

| 作業 | 作業用のブランチ | タグ（依頼者に渡すとき） |
| --- | --- | --- |
| 第N巻の VerM を作る | `work/volN-verM`（例 `work/vol6-ver2`） | `volN-verM`（例 `vol6-ver2`） |
| ガイドブック | `work/guide-verM` | `guide-verM` |
| 全巻にかかる修正（B 段階） | `work/allvol-…` | 終わったら巻ごとに `volN-verM` |
| 小さな直し | `work/fix-…` | なし |

- ブランチとタグに同じ名前を使わない（git が区別できなくなる）。そのため作業用のブランチは `work/` で始める。
- **版の番号は、これまでどおり依頼者に渡した順に数える。** タグは「渡したもの」にだけつけ、消したり付けかえたりしない。
- 移行のときの版（最初に `main` に入れるもの）は、第1巻 Ver4・第2巻 Ver4・第3巻 Ver3・第4巻 Ver2・第5巻 Ver4・第6〜9巻 Ver1・ガイドブック Ver1。最初のコミットに `migration-2026-10-31` のタグをつける（このタグでは組まない）。
- ただし第1巻・第2巻（と第5巻）は、`main` から組むと渡した版と一部のページの組み方が変わる（9章）。この変化は次の版（全巻にかかる修正の B 段階）で入る。

## 8. 委員会の作業と GitHub の対応

| 委員会の手順 | GitHub での形 |
| --- | --- |
| 依頼者の指示を受ける | チャット（または Issue）。チャットで受けた指示は、Claude が Issue に写す |
| 指摘を洗い出し、委員で修正方針を決める | `tools/FIX-*.md` に書いてコミット（これまでと同じ） |
| 直す | 作業用のブランチにコミット。1つのコミットは1つの直し（コミットの説明に指摘の番号を書く） |
| 組んで確かめる | 委員会の作業環境で組み、push すると Actions も組む |
| 委員会の最終確認 | プルリクエスト。確認の結果と議事録（`docs/議事録/`）を同じプルリクエストに入れる |
| 依頼者に渡す | 依頼者がプルリクエストを `main` に取りこむ（Merge）→ Claude がタグ `volN-verM` をつける → リリースができる |
| 依頼者からの指摘 | チャット、または Issue |

**リリースの形**：GitHub はリリースに添付するファイルの名前に日本語を使えない（英数字と一部の記号のほかは「.」に置きかえられる）。そこで次の2つを添付する。

| 添付するもの | ファイル名 | 画面に出る名前 |
| --- | --- | --- |
| 各 PDF | `vol6_Ver2.pdf`・`wrap6_Ver2.pdf` など | `第6巻_未来を計算する_Ver2.pdf`・`第6巻_カバー展開図_入稿用_Ver2.pdf` |
| 納品の名前の PDF 一式 | `vol6-ver2_pdf.zip` | `vol6-ver2_納品の名前のPDF一式.zip`（中のファイルは納品の名前） |

**納品物との対応**

| 納品物 | GitHub での場所 |
| --- | --- |
| PDF | リリース（タグごと）。途中の PDF は Artifacts |
| tex 一式（zip） | リリースの「Source code (zip)」（タグの時点のソース一式。書体・texmf を含み、これだけで組める） |
| 検算ファイル | `checks/`（問題の追加・訂正があったときだけ足す） |
| 議事録 | `docs/議事録/`（リリースの説明にも要点を書く） |

チャットでの納品（PDF・zip・議事録をこの会話に添付する形）も、依頼者が望むあいだは続ける。

## 9. 移行のときに確かめたこと

**第1巻・第2巻のちがいの原因**：原因は2つあった。

1. **ルビの位置の記録がこわれていた**：委員会の作業環境の `vol1.ltjruby`・`vol2.ltjruby` が、10月22日に組版が途中で止まったときに途中で切れていた。LuaTeX-ja はこわれた記録を黙って使わない（ログに1行出るだけで、エラーの数には入らない）ため、それ以後の第1巻 Ver4・第2巻 Ver4 はルビの記録なしで組まれていた。かっこのとなりのルビの位置などが少しちがい、第2巻では1か所で行の折り返しが変わって、さくいんのページが1つ動いた（「表計算ソフト」387→386）。
2. **渡した版のあとに直した共通部品**：第1巻・第2巻の Ver4（10月22日）のあと、第3〜9巻を作るあいだに共通部品（`bk-volume.sty`・`bk-b5.sty` など）を直している。今のソースで組むと、題名の2行目にルビがある章の初めのページで、章の帯と「道しるべ」の間が約 5 mm 狭くなり、ほかの章と同じ間になる（第1巻で16ページ）。こわれた記録をわざと入れて組んでもこの16ページは変わらなかったので、こちらは共通部品が原因である。

どちらも、今の組み方（まっさらな状態から、今の共通部品で組んだもの）のほうが正しい形である。

- 作業環境のこわれた記録は消した。`build.sh`・`ci-build.sh` は、こわれた記録を組む前に消し、読みこみの失敗をエラーとして数えるようにした（全巻にかかる修正事項 No.62）。
- `main` から組んだ第1巻・第2巻（と、同じ10月22日に組んだ第5巻 Ver4。第5巻は試していない）は、渡した版と少しちがう。この変化は「全巻にかかる修正」の B 段階で入る予定のもので、それまで第1・2・5巻の正式な PDF は渡した版のままとする。
- 10月30日に渡した「第1〜5巻の組版 tex 一式」も、その時点の共通部品が入っているので、組むと第1・2巻（と第5巻）は渡した PDF と少しちがう。
